# Design decisions

Each important choice was written down when it was made, with the options considered, what was good and bad about each, and the evidence. These are short summaries. Three of the eight rest on experiments against the real PayPal sandbox or the real Gemini API, not on documentation alone.

| # | Decision | Options weighed | Why this one | The cost we accepted |
|---|---|---|---|---|
| 0014 | One Go program, with the money maths in its own package | One Go program; several services; Python or a JavaScript stack | The fewest places to break in a one-week build; easy for a judge to run; the profit engine can be tested alone against hand-calculated answers | Less fashionable than a JavaScript front end |
| 0015 | The AI gets three jobs (understand, write, act) under code guardrails | AI reads only; three jobs under guardrails; a free-roaming agent | Real AI work where it is strong (reading people, writing like a person, acting through PayPal's toolkit), while every number and action stays under code. A free-roaming agent compounds errors and can misuse tools | More moving parts than "AI reads only" |
| 0016 | Gemini models, with two different models for the two readings | Gemini; Claude; both providers | One provider and one key for a short build; two different models give partly independent readings | Two models from one family share more blind spots than two providers would |
| 0017 | Guard against duplicate invoices with the invoice number, not PayPal's request id | Trust `PayPal-Request-Id`; remember requests ourselves; a fixed invoice number per deal and choice | **Tested in the sandbox:** two creates with the same request id made two invoices, while a reused invoice number was refused (`422 DUPLICATE_INVOICE_NUMBER`). The invoice number is enforced by PayPal itself, so it holds across crashes and restarts | Invoice numbers must be unique across all of the seller's invoices |
| 0018 | Start with two mid-size Gemini models and no billing | Mid-size models free; turn on billing for the strong models; switch accounts | **Tested against the API:** the strong models were refused on the free tier, while the mid-size ones answered. This keeps "two different models" at no cost, and billing can be added later if the exam shows it's needed | A weaker second reading than a strong model would give |
| 0019 | Read each email with `gemini-3.5-flash-lite` and `gemini-3.1-flash-lite` | That pair; keep an unlisted model with a 20-a-day limit; wait for a newer model that returned 503 | Ranked by "wrong but sure" first, then accuracy, then cost. The pair scored 0 wrong-but-sure, 20/20 and 6/6 mutations, and both are listed and reliable | Two "lite" models leave a smaller margin on harder emails |
| 0020 | The early-payment choice is a discounted draft due in 7 days ("plan B") | Wait for PayPal's early-payment rule; plan B; drop the choice | **Tested in the sandbox:** PayPal's early-payment rule returned 500 on every variant tried, while a discounted draft with a due date works. The percentage is the break-even of the cost of waiting, never a fixed 10% | The buyer gets the discount on the invoice even if they pay late; the screen tells the seller so |
| 0021 | PayPal's Agent Toolkit creates the draft; our REST client sets the due date | Toolkit, then REST; REST only | PayPal's own agent tool does the main work. Its schema can't set a due date, so a second call does. The seller approves both calls together under one fingerprint, and a failed second call is shown and resumable | Two calls, so the second can fail (handled and tested) |
